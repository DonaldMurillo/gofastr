# Historical upgrade fixtures

Two checked-in GoFastr apps, one generated by `gofastr@v0.38.0` and one by
`gofastr@v0.53.0`, that are mechanically upgraded to the current tree and
exercised, proving the `gofastr upgrade` path actually works end to end: an old
app builds, migrates over real existing rows, and serves its full contract after
the framework bump.

This fills the gap called out in the v1-readiness program: `gofastr upgrade` had
registry / detector / changelog-sync unit tests, but no checked-in old
application that was actually upgraded, built, migrated with existing data, and
hit over HTTP.

## Layout

```
evals/upgrade-fixtures/
  upgrade_fixtures_test.go     the driver (Go test, env-gated)
  regenerate-seed.sh           re-captures a fixture's seed.db from its old app
  fixtures/
    manifest.yml               expected post-upgrade row counts (the assertions)
    v0.38.0-app/               gofastr@v0.38.0 generated app (own go.mod)
      migration.patch          the manual source edits the upgrade needs
      seed.db                  frozen pre-upgrade SQLite DB (committed)
      gofastr.yml              the blueprint the app was generated from
    v0.53.0-app/               same shape, generated by gofastr@v0.53.0
    shape-zoo/                 one instance of each scanner shape, marked
    _shape-zoo.after/          the zoo's migrated files (underscore: the go tool skips it)
```

Each `<version>-app/` is its own Go module (own `go.mod`, pinned to that
release). The nested `go.mod` makes it invisible to the root `go build ./...`
and `go vet ./...`, so the fixtures never leak into the ordinary build or lint.

## What each fixture is

A small blueprint app (`gofastr.yml`, checked in for provenance) with three
entities: `users` (RBAC-gated), `tasks` (owner-scoped via `owner_field:
user_id`), and `tags` (public). Auth is wired in dev mode. The entity_list
screens give the app a real interactive surface (server-side sort + row-action
RPC). Each app was produced by running the matching old CLI's
`gofastr generate --from=gofastr.yml`.

`seed.db` is what booting that old app once leaves on disk: two registered users
(`alice@ex.com` / `bob@ex.com`, password `secret123`), three owner-scoped tasks
(alice owns two, bob owns one), and the three seeded tags. Regenerate it with
`regenerate-seed.sh` if a fixture's source ever changes.

One known generator bug is baked into both fixtures: `app.go` references
`context.Context` in the RBAC middleware closure but the v0.38.0 / v0.53.0
generators omitted the `context` import. The committed baseline includes the
one-line import fix (documented here, not in `migration.patch`, because it is a
same-version generator bug, not a cross-version migration step).

## What the driver does

Per fixture, `TestHistoricalUpgrades`:

1. Copies the fixture to a temp dir.
2. Scans it with the typed scanner (`internal/upgrade/scan`) as generated,
   still pinned to its own release (module proxy, cgo for the old sqlite
   driver): it must type-check there, and every `migration.patch` hunk that
   edits a `.go`, `.css`, `gofastr.yml` or `go.mod` file must be matched by
   some in-range note inside the hunk's old line range (a short, justified
   table exempts hunks no note can find — pure insertions with no retired
   spelling).
3. Adds `replace github.com/DonaldMurillo/gofastr => <repo root>` to its
   `go.mod`. This is how an unreleased bump lands without a published tag.
4. Scans again, still unpatched, against the current tree: the app must NOT
   type-check, every compile error the upgrade causes must be explained by an
   in-range note, breaking-note hits on Go/CSS files must land inside the
   patch's old ranges, and one `gofastr upgrade` CLI smoke run keeps the
   shipped binary path covered.
5. Applies `migration.patch`: the manual Go-source edits `gofastr upgrade
   --apply` cannot do, one hunk per registry note (`internal/upgrade/releases/`).
   A third scan asserts no breaking note's strings/css/config/gomod matcher
   still hits (no retired spelling survived) and that the app type-checks again.
6. Runs `go mod tidy` + `go build` (the mechanical steps `--apply` runs).
7. Boots the upgraded binary against a copy of `seed.db`.
8. Asserts, over HTTP (no browser):
   - SSR renders (`GET /`, `GET /tags` → 200).
   - Public CRUD survives (`GET /api/tags` → the seeded count).
   - OpenAPI is auth-gated (401 anon, 200 authed) and names every entity.
   - Both seed users log in. Their password hashes survived the migration.
   - Owner isolation: alice sees only her tasks, bob only his; alice's create
     is invisible to bob.
   - Create stamps the owner from the session.
   - The entity_list sort round-trips (`?sort=` changes order) and a row-action
     RPC (`DELETE /api/tags/{id}`, the `data-cui-rpc` target) round-trips.

`TestUpgradeFailsWhenMigrationSkipped` is the negative proof: it deliberately
skips `migration.patch` and asserts `go build` fails with an actionable error
naming the removed `EntityConfig` fields. A green build there would mean the
driver cannot detect a skipped upgrade step, which defeats its purpose.

The registry-side gates live beside the driver:
`TestRegistrySymbolsExistedAtPriorTag` reads each note's `uses`/`fields`
symbols and `imports` paths out of the git history at the newest tag below
the note's release (syntactically, via `go/parser` over `git show`), so a
typo, or a symbol spelled at its HEAD path when it lived elsewhere back then,
fails the job instead of silently matching nothing. It needs the repo's tags:
locally `git fetch --tags origin`; the CI job checks out with
`fetch-depth: 0`.

`TestRemovedExportsHaveNotes` is the inverse. It diffs the exported API of
the module's public packages (everything outside `internal/`, `cmd/`,
`examples/`, `evals/`, `benchmarks/`, `testdata/` and nested modules)
between each release from v0.86.0 on and the tag below it, then between the
newest tag and the working tree. Every removed package, package-level name,
or field or method of a surviving type must be found by a note in the
releases between the two: a `uses`, `shapes` or `fields` entry naming it, or
an `imports` entry covering its package. v0.86.0 removed 68 exported
identifiers and shipped notes for 48 of them, so `gofastr upgrade` stayed
silent on the other twenty while the code that used them no longer
compiled. Releases before v0.86.0 are not audited. Without the tags
it fails with how to fetch them, the same as the symbol gate.

## The shape zoo

`fixtures/shape-zoo/` is a small app pinned to `gofastr@v0.63.0` that holds
one instance of each code shape a reviewer found the scanner misreading:

- a method implementing a kit interface from a package that never imports it;
- a type alias of a kit type;
- an `ExtraAttrs` map key set in another file, in another case;
- an unsafe `FormConfig.Action` behind a constant;
- class markup spelled the way a browser forgives (unquoted, upper case,
  character references), next to spellings it must not read (a second class
  attribute, script text, a comment);
- CSS escapes;
- `t.Setenv` beside testing failure messages;
- a sheet-name constant in another package;
- a `//go:build windows` file;
- a nested module, and one under `testdata/` that must stay unread;
- a package-local alias in a compile error.

Each line the scan must report carries a `zoo:hit <tag>` comment naming the
note. A line only a compile error reaches (an interface assertion whose
implementation changed elsewhere) carries `zoo:err <tag>`. `TestShapeZoo`:

1. Scans the zoo at v0.63.0. It must type-check, leave nothing unscanned, and
   hit exactly the `zoo:hit` lines: a missed marker and an unmarked hit both
   fail, naming the line.
2. Points it at this tree. Nothing type-checks, every compile error is
   explained, and each hit read from an error sits on a line marked for its
   note.
3. Copies `fixtures/_shape-zoo.after/` over it (the migrated files) and runs
   the same post-patch gate as the historical fixtures.

A new reviewer-found shape goes into the zoo with its marker, in the same
change as the fix.

## The migration itself (what's in migration.patch)

Two documented registry notes, identical for both fixtures:

- **v0.54.0, grouped EntityConfig.** The flat `OwnerField` / `Public` / `CRUD`
  / `MCP` / `Access` fields move to `Scope` and `Exposure`. `migration.patch`
  rewrites the three `app.Entity(...)` calls in `entities/{tasks,tags,users}.go`.
- **v0.56.0, pure-Go sqlite.** `mattn/go-sqlite3` is replaced by
  `github.com/DonaldMurillo/gofastr/sqlite/stdlib` (modernc), so the upgraded
  app builds and runs with `CGO_ENABLED=0`. The `sql.Open("sqlite3", …)` call is
  unchanged because the stdlib package registers the `sqlite3` name.

- **Unreleased, the table's typed sort props.** `ui.DataTableConfig`
  drops `SortHrefPattern` (the caller-assembled `"?" + carry +
  "sort=%s&dir=%s"` pattern string) for `Query url.Values`: the carry
  the old pattern hand-built (`q=` plus escaped facet pairs) becomes
  `query.Set` calls, and every sort href is built through `net/url`
  with the parameter replaced rather than spliced.
- **Unreleased, the typed pager.** `ui.DataTableConfig.Pagination` is a
  `*ui.PaginationConfig` (`Pages`/`Page`/`Query`, the headless
  pager's props) and `core-ui/patterns/pagination` is deleted. The
  fixture's `&pagination.Config{Total: pages, Current: page,
  HrefPattern: "…"}` becomes `&ui.PaginationConfig{Pages: pages,
  Page: page, Query: query}` — the same map the sort props carry.

- **Unreleased, `ui.FormFieldConfig.Input` is a builder.** The field hands its
  control an id, an `aria-describedby` and an invalid state before the control
  renders, replacing the attribute splicing that injected them afterwards.
  `migration.patch` threads a `headless.FieldControl` through the fixture's own
  `formInput` and puts those three onto every control it builds — a closure
  that ignores the argument compiles and silently drops the wiring, which is
  the defect the builder exists to prevent.

  These unreleased steps had **no registry notes** when the fixtures were
  written (the registry is keyed by released version and its `through:`
  marker is pinned to the newest CHANGELOG release heading; two tests
  enforce both). The coverage gate now enforces their arrival: it fails on
  the hunks they explain until the notes carrying the release land in
  `internal/upgrade/releases/`, so a forgotten entry cannot merge quietly.

Everything else the v0.38.0 / v0.53.0 generators emitted (the screens, the auth
wiring) compiles against the current tree unchanged.

## Running

```sh
# locally (builds + boots both fixtures; ~seconds warm, longer cold)
GOFASTR_UPGRADE_FIXTURES=1 go test ./evals/upgrade-fixtures/ -count=1 -v

# negative proof only
GOFASTR_UPGRADE_FIXTURES=1 go test ./evals/upgrade-fixtures/ \
  -run TestUpgradeFailsWhenMigrationSkipped -count=1 -v

# the shape zoo only (seconds; needs the module proxy)
GOFASTR_UPGRADE_FIXTURES=1 go test ./evals/upgrade-fixtures/ \
  -run TestShapeZoo -count=1 -v
```

The env gate keeps the driver out of `go test ./...` (it shells out, fetches
modules, and boots servers). The CI job `upgrade-fixtures` sets the env var.

## CI

Blocking since 2026-08-16 (promoted after a stretch of green runs). It runs
the whole package — the driver, the negative proof, and the registry symbol
gate — against the current tree, checks out with `fetch-depth: 0` so the tags
the symbol gate reads are present, restores the per-SHA Go cache the `test`
job writes, and is bounded by a 25-minute timeout (the own-version scans
compile the old eras' module trees, including the cgo sqlite driver).

## Adding a new fixture

1. `go install github.com/DonaldMurillo/gofastr/cmd/gofastr@vX.Y.Z` to a temp
   GOBIN.
2. Generate from a blueprint (or reuse `fixtures/v0.38.0-app/gofastr.yml`),
   `go mod init`, `go get gofastr@vX.Y.Z`, `go mod tidy`, and confirm it builds
   at its own version.
3. `regenerate-seed.sh evals/upgrade-fixtures/fixtures/vX.Y.Z-app` to capture
   `seed.db`.
4. Point it at the current tree (`replace`), `go build`, and `git diff` the
   source edits into `migration.patch`. Add the row counts to `manifest.yml`.
5. Append a `{name, from}` pair to `historicalFixtures` in the driver.
