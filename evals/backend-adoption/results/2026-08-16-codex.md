# Codex backend rerun — 2026-08-16

This run measures one thing: whether the discovery cost the 2026-07-26 study
found — 313,579 cold-start tokens for GoFastr against Gin's 72,172 — moved
after the changes on the `claude/go-faster-dev-experience-ri6nzs` branch
(PR #200): the `backend-capability-map` doc linked first from the generated
`AGENTS.md`, OpenAPI path keys that match live routes, and a dependency graph
cut from 95 modules to 57. It is next-move #6 from that study's list, run to
completion; it is not a rerun of the full three-framework study.

## Protocol

- Codex CLI `0.145.0` — the same version as 2026-07-26 — CLI default model.
- Two independent cold starts each for GoFastr and Gin. Gin is here as a
  drift control: if the served default model's spending habits changed since
  July, Gin shows it. `net/http` was not rerun.
- Framework under test: commit `79bc76bd` of PR #200. The harness builds the
  `gofastr` CLI from the checkout and `replace`s the module to the repo root,
  so the scaffold the agent receives is this branch's.
- Task, grader, and scoring identical to 2026-07-26.

Raw artifacts are in `dist/backend-adoption/20260816T062854Z/`.

The control is the load-bearing row. Same CLI version, same task, and Gin's
cold starts cost 34% more than in July — the served default model spends more
tokens now. Against that headwind GoFastr's absolute spend fell 25%, and the
ratio — the number that measures discovery cost relative to a framework the
model already knows — fell from 4.35× to 2.42×.

What the ratio does not tell you is which branch change did the work. The
capability map, the OpenAPI path fix, and the 40% smaller dependency graph
all landed together; this run measures their sum.

## The failed run

GoFastr run 1 scored 85: cross-owner GET answered 404 and the list leaked
nothing, but cross-owner PATCH answered `400 "status must be closed"` where
the grader requires 404 — the handler validated the payload before the
owner-scoped lookup, telling a foreign user the ticket exists and what state
it is in.

That handler is the agent's own. Run 1 hand-rolled its REST layer —
`r.PatchFunc` over a bespoke store, suppressing the `GOFASTR1902` contract
finding with a `//gofastr:allow` — and made the classic
validate-before-authorize mistake in its own code. Run 2 declared the entity
(`fw.Entity` with `Scope.OwnerField` and custom `entity.Endpoint`s) and
scored 100/100 on both phases. The July study's two runs both used the
declarative surface and both got isolation right. Across the two studies the
pattern is consistent: the framework surface gets ownership right; the agent's
hand-rolled substitute is where the authorization bug appears.

## Limitations

- Two repetitions per lane. The GoFastr cold spread (205k–262k) is wide
  relative to the July delta; read the direction, not the digits.
- The CLI default model is not pinned server-side. The Gin control bounds the
  drift but cannot remove it.
- The three branch changes are not separable in this design; attributing the
  delta to the capability map alone would overclaim.
- Everything the July study lists — grader scope, GoFastr's browser-review
  instructions, Gin as a router rather than a feature-equivalent framework —
  still applies.
